# Roadmap

There are two kinds of repo. This one is public and holds generic tools and documentation.
Each house has its own private **site repo**: `site.yaml`, the unpacked OM project, the
house's own Lua scripts, and its notes. A site repo uses this package; nothing
house-specific lives here.

## Phase 1: extract the code (done 2026-11-04)

- [x] `grenton_kit` package with the `grenton` CLI (uv)
- [x] `omp`: unpack, pack, import-workspace, event, script and feature edits; the project
      key is kept out of git
- [x] `mygrenton build`: pages, dimmers (DIMM, DALI), on/off (DOUT, or a dimmer with an
      on/off load), THERMOSTAT_V2, temperature values, setpoint sliders, from `site.yaml`
- [x] `ha call` and `ha sync`: areas, names, entity ids, switch_as_x, groups, °C,
      dashboard (written only when it differs)
- [x] Acceptance on the first house:
  - the interface is byte-identical
  - `.omp` packing is byte-identical
  - the HA dry run plans one change, a thermostat order on the dashboard that now
    follows `site.yaml`
- [x] Tests on a synthetic house (`tests/fixtures/house`)

## Phase 2: switch the first site repo over (done 2026-11-04)

- [x] The site repo depends on this package through a uv path dependency (`../grenton-home-assistant-kit`).
- [x] Its copies of the tools are deleted.
- [x] House logic (button bindings, heating scripts) stays in the site repo and imports
      `grenton_kit.omp`. Re-running it leaves the project byte-identical. It may later
      become a config-driven "event commands" feature here.

## Phase 3: onboarding (built 2026-11-04; the interview is untested with a real new user)

- [x] `grenton discover` reads the project and writes `inventory.md`. It lists:
  - CLUs, flagging renamed ones (nameOnCLU)
  - lights with what controls them (panel buttons, group scripts)
  - relays classed as heating, switched, scripts only or unused
  - thermostats with sensor and output, panels, scripts, and existing interfaces

  It also writes a first `site.yaml`, or `site.draft.yaml` if one exists. Rooms are
  guessed from the controlling panel, then the object name, then group panels. Labels
  are reused from an existing interface.
- [x] `grenton init <folder> --omp <file>` creates a site repo:
  - takes the key from the `.omp` into `secrets/` (mode 600), unpacks, discovers
  - writes README, CLAUDE.md, the docs (STATUS has an onboarding checklist) and the
    `/onboard` skill
  - commits, and refuses to commit secrets
- [x] `grenton ha blink` flashes a light and restores its state, to find unknown outputs.
- [x] `/onboard` skill (`templates/skills/onboard/SKILL.md`, copied into each site repo).
- [x] Acceptance, mechanical part, on the first house from scratch:
  - `init` from its `.omp` gives an identical project and the same key; nothing secret
    is committed
  - the draft builds without edits
  - all 33 named lights and 12 thermostats are found, and 33 of 33 labels are reused
  - rooms are right for 23 of 33 lights
  - the rest are questions for the interview: lights controlled through group panels,
    the garage relays, a dimmer with no name
- [x] Acceptance, interview part: the first house's owner ran `/onboard` on a fresh copy
      (2026-11-04): "Looks really good." Changed after it: one question at a time, with
      suggested replies (AskUserQuestion), instead of batches.
- [ ] `blink` tested on site.

## Phase 5: tests and CI (done 2026-11-04)

- [x] The synthetic house is generated by `tests/fixtures/make_house.py` in Object Manager's
      exact file formats: XStream XML, and Jackson JSON with `"key" : value`. The edit
      tools match that formatting.
- [x] Tests for:
  - event commands: add to empty and full events, remove back to OM's own form,
    replace, clear
  - features: both files, nothing else touched, isDirty
  - scripts: add with parameters, set, a first script on a CLU, files and manifest
  - edits surviving pack, pack refusing files missing from the manifest
  - import-workspace: changed and new files, re-redaction, keep or delete missing files,
    no project open
  - a changed project key, and the CLI against a site
- [x] GitHub Actions: pytest on Python 3.11 and 3.13, plus a check that the fixture
      matches its generator.

## Phase 6: publish

- Make the repo public and post on the HA community and Grenton forums.
- Separately, contribute THERMOSTAT_V2 support to the HA Grenton integration.

## Known limits

- Tested with one Object Manager version and one house.
- The HA Grenton integration has no reconfigure. After an interface change, delete the
  integration entry and add it again. Entity unique ids are the widget dtoIds, which are
  stable, so names and areas survive.
